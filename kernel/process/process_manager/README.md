# process_manager

这个目录负责进程记入账本之后的事。创建本身在 `process_creat`：找到插件、打启动包、脱离拉起一个进程。资源里装什么由资源池决定，不在这里。业务消息走当前选中的通信通道，默认是账本信箱。资源、启停和编制仍读写同一份账本。

这里分成三块：

- **一份进程。** 等它就绪，给它派活，让它停下，崩了就把资源还回去。
- **一组进程。** 同一个能力该有哪几份在岗，缺了开谁，多了关谁。
- **怎么调用。** 调用马上拿到回执，想等再等。先后、同时、做完再汇总放在插件外面。

## 文件

- `__init__.py`：对外导出进程对象、启动包和状态名字。
- `lifecycle.py`：进程状态。刚建好、启动中、运行中、停止中、已停止、失败。
- `supervisor.py`：账本上的一份进程。`submit` 把业务请求交给当前通道并返回 `Receipt`，`wait` 再取结果，`wait_first` 收先完成的那张。`send` 是提交后立刻等待。停止只把期望状态写成 `stop`。作废句柄只改账本里的句柄状态。
- `compose.py`：插件外面的拼装。`Call` 是一次还没发出的调用，`chain` 做完再做下一个，`group` 一起发出，`chord` 等它们做完再提交一条新消息。
- `delegation.py`：等待回执时的两条规矩。手里还占着另一份独占进程就不能等。同步委托绕回自己就拒绝。
- `liveness.py`：问一个进程号是不是还活着，而且是不是原来那一个。Windows 上只查询，不发会杀掉进程的信号。身份对不上就不当成还活着。存活以账本里的 pid 为准。
- `capability_process.py`：旧的导入路径。内容在 `supervisor.py`，这个文件只把原来的名字指过去。

## replica_layout

编制。同一个能力该有哪几份进程在岗。它对比已经在跑的，给出要新开哪些、要关掉哪些。真正拉起进程的是调和器，用的是 `process_creat`。

开发者按同一套接口登记自己的规则。接口、参数和三种内置规则写在 [replica_layout/README.md](replica_layout/README.md)。

- `layout.py`：共用的名单和两个必答问题。现在该有哪些份，以及对比正在跑的，哪些要开、哪些要关。
- `registry.py`：按名字登记和取出。调和器不导入某一种布局的类。
- `numbered/`：固定编号。空出来的号仍用原来的号补上。
- `counted/`：只盯着份数。少了补最小的空号，多了关号最大的。
- `named/`：按给定的名字开关。名单里没有的，正在跑的会放进要关掉的那一份。
